# WilList: instructions for coding agents

WilList is a student planner built on Brian Tracy's ABCDE method (A1 first, plan tomorrow tonight, written goals).
The **iPhone app is the main product** (`ios/`, SwiftUI, iOS 18 and later).
The website (`app/`, plain JavaScript, no build step) is the older version and comes second.
The owner is Willis Liao (GitHub `WillisLiao`).

This file carries everything an agent needs, so a fresh machine with no personal settings, skills or memory can continue the work.

## Read first, every session

1. `handoffs/HANDOFF.md`: the living snapshot of where things stand. Read it before anything else.
2. `handoffs/OWNER-REQUESTS.md`: every request the owner has made and where it stands. The newest direction (2026-10-24) changes the product: iPhone and Mac only, no website, no iCloud, sign-in with Google, Facebook and Apple, an Agent tab and a Progress tab.
3. The newest `handoffs/NEXT-SESSION-*.md`: the work that is ready to pick up.
4. `docs/DESIGN.md`: the app's design system and the SwiftUI pitfalls already paid for.
5. `docs/PRINCIPLES.md`: every Tracy principle and where it lives in the app. Keep all of them.
6. The newest file in `devlogs/` if you need the history behind a decision.

## Setup on a new Mac

- Xcode 26 or later (it was last built with Xcode 27.1; the iOS 26 SDK is needed to compile, and the app still runs on iOS 18), with an iOS Simulator runtime (`xcodebuild -downloadPlatform iOS`).
- Node 22 or later. There are no npm dependencies to install; scripts use `npx --yes` where needed.
- Do not run `playwright install`.
- Installing on real devices needs Willis's Apple developer team (`45MSS5RXML`, bundle id `com.lull.willist`): sign in to that Apple ID in Xcode, Settings, Accounts. Simulator work needs no account.

## Commands

| What | Command |
|---|---|
| Swift core tests (planner, parser, importer, Claude request) | `cd ios/WilListCore && swift test` |
| Build the iPhone app (device, release) | `xcodebuild -project ios/WilList.xcodeproj -scheme WilList -configuration Release -destination 'generic/platform=iOS' -derivedDataPath build/ios -allowProvisioningUpdates -quiet build` |
| Screenshots in the simulator, sample data loaded | `npm run ios:shots` (see the top of `scripts/ios-shots.mjs` for the debug launch arguments that open any screen) |
| Install on every paired iPhone and iPad on this Wi-Fi | `npm run ios` (`npm run ios -- iphone` for one) |
| Website unit tests | `npm test` |
| Website end-to-end test | `npm run test:e2e` |
| Lint | `npm run lint` |
| Run the website locally | `npm start`, then http://localhost:8080 |

Done means: `swift test`, `npm test`, `npm run lint` and `npm run test:e2e` pass, the app builds with zero warnings, and you have looked at the changed screens in the simulator.

## Standing rules from the owner

- Never use the em dash. Use a plain dash "-" or rewrite the sentence.
- In Markdown files you write or substantially edit, put each full sentence on its own line.
- Commit messages: plain, descriptive, and **never** add an AI co-author line or any agent attribution.
- Do not open a pull request unless asked.
- Do not merge into `main` without asking first: a push to `main` runs the GitHub Pages deploy in `.github/workflows/pages.yml`, and publishing the website is the owner's call. Work on a branch and push it.
- Never commit API keys or personal data. The Anthropic key lives only in the device keychain.
- Never modify `CHANGELOG.md` or files marked auto-generated by hand.
- Prefer quality, simplicity, robustness and long-term maintainability over development cost.
- Bug fixes start by reproducing the bug end to end, the way a user would hit it (in the simulator for the app).
- Be picky about the UI you see and aim for pixel perfection. If something clearly looks off, even if it is unrelated, fix it along the way.
- Same standard for engineering: if you see a lint error, a failing test or a flaky one, fix it even if you didn't cause it.
- For narrow lookups and research, send a cheap, fast subagent (a Haiku model) to scout instead of reading everything yourself.
- Ask before anything outward-facing or hard to undo (publishing, deleting, messaging, purchases).

## Product rules

- Keep every Tracy principle in `docs/PRINCIPLES.md`.
- Simplicity first: the owner has said more than once that the app felt busy and confusing. Each screen has one job, one primary action, and as few words as do the job.
- Logging and ticking off must be fast and satisfying (tick, chime, haptic, the row glides away).
- There are no fixed visual rules: on 2026-10-23 the owner said "there are no rules, for anything" and asked for a visually captivating experience. Today the app is in the Lagoon look the owner picked on 2026-10-23 (one teal, system type, the A1 on a pale teal card), laid out like its widgets: white cards on a deep slate on every tab, sheets on a light blue-grey, the letters in red, orange, yellow, green and blue from A to E, course colours on what belongs to a course, and red words only for problems; change any of it when it makes the app better.
- Phone first, keyboard access, reduced motion respected, VoiceOver labels on every control.
- Website only: no native `alert`, `confirm` or `prompt`; fonts stay self-hosted.
- The save file format is shared with the website (`willist.v1`): only add optional fields, decode leniently, never break older saves.

## Design work

For any task that designs, builds, reviews or substantially changes UI, load and follow the two design skills kept in this repo:

- `.claude/skills/frontend-design/SKILL.md` (Anthropic, Apache 2.0): a distinctive point of view, plan before building, critique from screenshots.
- `.claude/skills/taste-skill/` (MIT): for app screens follow `references/app-screens.md` (colour on data only, one primary action, honest zeros, sentence case, no ornaments).

Claude Code loads skills from `.claude/skills/` automatically. Other agents can read the `SKILL.md` files directly.
Then follow `docs/DESIGN.md`, which turns both into WilList's own rules, and Apple's Human Interface Guidelines.
